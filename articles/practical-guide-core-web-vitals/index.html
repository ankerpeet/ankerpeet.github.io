A practical guide to Core Web Vitals for busy teams

What LCP, INP, and CLS actually measure, why your numbers don't match, and where to spend your time first.

By Anker PeetOctober 7, 20269 min read

In this article

  1. The three metrics in plain language
  2. Lab data vs. field data
  3. Fixing slow LCP
  4. Fixing poor INP
  5. Fixing layout shift
  6. Where to start

Performance work has a reputation for being a rabbit hole. There are dozens of metrics, hundreds of tools, and endless advice about micro-optimizations. Core Web Vitals cut through a lot of that noise by focusing on three questions every visitor implicitly asks:

  • Is it loading? Can I see the main content yet?
  • Is it responding? When I tap or type, does something happen right away?
  • Is it stable? Does the page stay put, or does it jump around while I'm reading?

Answer those well and your site will feel fast. This guide explains each metric, why the numbers you see often disagree, and the fixes that tend to deliver the biggest improvements.

The three metrics in plain language

Core Web Vitals thresholds
MetricWhat it measuresGoodPoor
LCP
Largest Contentful Paint		How long until the largest visible image or text block renders≤ 2.5 s> 4 s
INP
Interaction to Next Paint		How quickly the page visually responds to clicks, taps, and key presses≤ 200 ms> 500 ms
CLS
Cumulative Layout Shift		How much visible content unexpectedly moves around≤ 0.1> 0.25

Google evaluates these at the 75th percentile of real page loads, split by mobile and desktop. In practice, that means you need most of your visitors to have a good experience, including people on slower phones and networks, not just the typical visitor on a fast laptop.

INP replaced First Input Delay (FID) as a Core Web Vital in 2024. It's a much stricter metric: FID only measured the delay before the first interaction started processing, while INP looks at the full response time across interactions throughout the visit.

Lab data vs. field data

The most common question I hear is: "Lighthouse says we're fine, so why does Search Console say we're failing?" The answer is that they measure different things.

  • Lab data (Lighthouse, WebPageTest, Chrome DevTools) runs one simulated page load on one device profile. It's repeatable and great for debugging, but it isn't your users.
  • Field data (the Chrome UX Report, Search Console, or your own real-user monitoring) comes from actual visits. It reflects real devices, networks, cache states, logged-in pages, and user behavior.

Field data is the scorecard; lab data is the diagnostic tool. Lighthouse can't measure INP at all in a standard page load because no one is interacting with the page. If your field INP is poor, you need to reproduce the slow interactions manually, with DevTools' Performance panel and CPU throttling turned on.

Optimize for field data. Use lab tools to understand why the field numbers look the way they do.

Fixing slow LCP

LCP is usually a hero image, a large heading, or a banner. Slow LCP almost always comes down to one of four phases: the server responds slowly, the browser discovers the LCP resource late, the resource takes too long to download, or rendering is blocked after it arrives.

Make the LCP image discoverable and prioritized

If your LCP image is set via CSS background-image or injected by JavaScript, the browser can't find it until much later. Use a real <img> in the HTML and tell the browser it matters:

<img
  src="/img/hero-1200.jpg"
  srcset="/img/hero-600.jpg 600w, /img/hero-1200.jpg 1200w"
  sizes="100vw"
  width="1200" height="600"
  alt="Team reviewing a website report"
  fetchpriority="high">

Never lazy-load the LCP image

Adding loading="lazy" to every image is a common "optimization" that actively hurts LCP. Lazy-load images below the fold; load the hero eagerly.

Right-size and compress

Serve modern formats like AVIF or WebP, and use srcset so phones don't download desktop-sized images. A 2 MB hero image on a mobile connection will dominate your LCP no matter what else you do.

Reduce render-blocking resources

Large CSS files and synchronous scripts in the <head> delay the first render. Load non-critical scripts with defer or async, remove unused CSS, and be skeptical of third-party tags that load before your content.

Fixing poor INP

INP problems are almost always JavaScript problems. When the main thread is busy running a long task, the browser can't respond to the user's click until that task finishes.

Break up long tasks

Any task over 50 ms is considered "long." If an event handler does a lot of work, do the visible update first and yield back to the browser before continuing:

button.addEventListener('click', async () => {
  showSpinner();            // update the UI first

  await yieldToMain();      // let the browser paint
  await doExpensiveWork();  // then do the heavy lifting
});

function yieldToMain() {
  if ('scheduler' in window && 'yield' in scheduler) {
    return scheduler.yield();
  }
  return new Promise((resolve) => setTimeout(resolve, 0));
}

Audit third-party scripts

Analytics, tag managers, chat widgets, A/B testing tools, and ad scripts all compete for the same main thread. List every third party, what it's for, and who owns it. It's common to find scripts that nobody remembers adding.

Ship less JavaScript

Code splitting, removing unused dependencies, and avoiding heavy client-side rendering for mostly static content all reduce the amount of work the main thread has to do, especially on mid-range Android phones where most INP problems show up.

Fixing layout shift

CLS is the most frustrating metric for users: you go to tap a link and an ad loads, pushing it out from under your finger. Fortunately, it's often the easiest to fix.

  • Always set image and video dimensions. Add width and height attributes (or CSS aspect-ratio) so the browser reserves space before the file loads.
  • Reserve space for dynamic content. Ads, embeds, cookie banners, and "you might also like" sections should have a fixed minimum height, or appear in overlays that don't push content.
  • Tame web fonts. A fallback font with very different metrics causes text to reflow when the web font arrives. Use font-display: swap together with fallback metric overrides like size-adjust, or preload your most important font file.
  • Animate with transforms. Animating top, height, or margin moves surrounding content; transform doesn't.

Where to start

If you only have a few hours this sprint, here's the order I'd recommend:

  1. Check field data first. Look at Search Console's Core Web Vitals report or PageSpeed Insights for your key templates. Find out which metric is failing, and on which device type.
  2. Focus on your highest-value templates. Home page, product or service pages, and checkout or contact flows matter more than the blog archive.
  3. Fix the LCP element. Make it discoverable, prioritized, and correctly sized. This is often the single biggest win.
  4. Add dimensions to every image. A quick sweep usually eliminates most layout shift.
  5. Inventory third-party scripts. Remove what you don't need and defer what you do.

Performance isn't a one-time project. New features, new marketing tags, and new images will slowly erode your gains. Add a performance budget to your build, monitor field data monthly, and treat regressions like bugs.
