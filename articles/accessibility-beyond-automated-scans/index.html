What automated accessibility scans miss (and how to catch it)

Automated checkers are a useful first step. I wouldn't treat a clean report as proof that people can use the site, though.

By Anker PeetOctober 7, 20268 min read

In this article

  1. Why scanners fall short
  2. Seven things I check by hand
  3. A 30-minute manual check
  4. Building accessibility into how you ship

Tools like Lighthouse, axe, and WAVE have made accessibility testing easier. You run a scan, get a list of issues, and fix what it finds. That's useful. But what happens after the score turns green? It's easy to close the ticket and assume the site is accessible.

I've seen sites with near-perfect scan results that still don't work with a keyboard. I've also seen forms where a screen reader user can submit the whole thing without hearing what went wrong. The scanner didn't make a mistake; it just couldn't check those parts of the experience.

What a scan can and can't tell you

Automated tools are good at checking things they can infer from the code. Does an image have an alt attribute? Is the text contrast high enough? Does an input have a label? They have a harder time with things that require judgment or actually using the page.

A scan can tell you an image has alt text, but not whether that text says "image123.jpg." It can find a button, but it can't press Tab through the page and notice that focus disappears behind a sticky header.

Automated testing can tell us whether code follows certain rules. Manual testing helps us find out whether someone can complete the task.

The Web Content Accessibility Guidelines (WCAG) 2.2 describe what people need, not just what the code should look like. That's why a machine can't fully check every guideline.

Seven things I check by hand

1. Keyboard traps and illogical focus order

Some people navigate with a keyboard or a device that works like one. Custom dropdowns, carousels, date pickers, and dialogs can be tricky. A scan won't tell you if focus gets stuck inside a widget (2.1.2 No Keyboard Trap) or jumps around in a way that makes the page hard to follow (2.4.3 Focus Order).

2. Focus that's invisible or hidden

I still see sites remove the browser's focus outline with outline: none. A focus style can also be there but hidden behind a sticky header, cookie banner, or chat widget. WCAG 2.2 calls out this issue in 2.4.11 Focus Not Obscured (Minimum), and it can depend on where you've scrolled. That's one reason a scan may miss it.

This is a simple starting point:

:focus-visible {
  outline: 3px solid #4f43c9;
  outline-offset: 3px;
}

/* Keep focused elements clear of a sticky header */
html {
  scroll-padding-top: 5rem;
}

3. Meaningless accessible names

A scan can check whether a link or button has a name. It can't tell you if a page has twelve links that all say "Read more," or an icon button that a screen reader announces only as "button." People often move through a list of links or buttons, so each one should make sense on its own.

<!-- Ambiguous -->
<a href="/pricing">Read more</a>

<!-- Clear, without changing the visual design -->
<a href="/pricing">
  Read more<span class="visually-hidden"> about pricing</span>
</a>

4. Form errors nobody hears

Here's a common example: someone submits a form, a red border appears around a field, and nothing else happens. If you're looking at the screen, you may notice it. If you're using a screen reader, you may not hear anything. Good error handling identifies the field (3.3.1 Error Identification), explains what went wrong, suggests a fix where possible (3.3.3 Error Suggestion), and makes sure the message is announced or easy to find.

WCAG 2.2 also added 3.3.7 Redundant Entry. The idea is straightforward: don't make people enter the same information twice in one process, like asking for a shipping address again on the billing step.

5. Small or crowded touch targets

WCAG 2.2's 2.5.8 Target Size (Minimum) says buttons and links should be at least 24 by 24 CSS pixels, or spaced far enough apart to avoid accidental taps. Tiny close icons, cramped pagination, and tightly packed social icons are common examples. A tool can flag some of these, but deciding whether an exception applies (such as a link in the middle of a sentence) still takes judgment.

6. Interactions that require precise movement

2.5.7 Dragging Movements says that anything people can drag needs another way to complete the same action. That might be a sortable list, slider, or map pin. If dragging is the only option, someone with tremors or using voice control may get stuck. You could add "move up" and "move down" buttons or let people enter a value instead.

7. Content that breaks when zoomed

1.4.10 Reflow says content should work at 320 CSS pixels wide without requiring horizontal scrolling. That's roughly what you get by zooming a 1280-pixel-wide browser to 400%. Fixed-width containers, sticky elements that take up too much space, and data tables can cause trouble. A scan won't zoom in for you.

A 30-minute manual check

You don't need special tools to find many of these issues. Pick an important task people do on your site, like signing up, checking out, or requesting a quote, and try it this way:

  1. Put the mouse aside. Complete the task with Tab, Shift+Tab, Enter, Space, Escape, and the arrow keys. Can you see where focus is? Can you reach and use everything? Can you close every menu and dialog?
  2. Zoom to 400%. In a 1280-pixel-wide window, zoom the browser to 400%. Does anything get cut off or overlap? Do you have to scroll sideways to read?
  3. Try submitting a form with errors. Leave required fields empty or enter something invalid. Are the errors explained, connected to the right fields, and easy to find?
  4. Try a screen reader for five minutes. VoiceOver comes with macOS and iOS; NVDA is free on Windows. Move through the headings and links. Does the page structure make sense? Do the controls tell you what they do?
  5. Listen to the content. Check the alt text on important images and the headings on key pages. Would they make sense without the visual layout?

Write down where you got stuck or confused. I think that list is often a more useful starting point than a score.

Make accessibility part of the work

An audit can help you see where to begin, but it works better as part of an ongoing process. Teams that keep accessibility on track tend to do a few things regularly:

  • Run automated checks in CI so regressions in the easy-to-detect issues never reach production.
  • Add a short keyboard-and-zoom check to the definition of done for new UI.
  • Build accessible patterns once in a shared component library, then reuse them everywhere.
  • Re-test key journeys after major redesigns or new feature launches.

Automated scans and manual testing do different jobs. I use scans to catch the issues they can find quickly, then test the experience itself to see where people may run into trouble.
