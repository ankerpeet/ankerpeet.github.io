What automated accessibility scans miss (and how to catch it)

Automated checkers are a great first step. But a clean report doesn't mean people can actually use your site.

By Anker PeetOctober 7, 20268 min read

In this article

  1. Why scanners fall short
  2. Seven things scanners routinely miss
  3. A 30-minute manual check
  4. Building accessibility into how you ship

Tools like Lighthouse, axe, and WAVE have made accessibility testing far more approachable. Run a scan, get a score, fix the red items. It feels like progress, and it is. The problem is what happens next: the score turns green, the ticket gets closed, and the team assumes the site is accessible.

In audits I regularly find sites with near-perfect automated scores that a keyboard user can't get through, or where a screen reader user can fill out an entire form without ever hearing what went wrong. The scanner wasn't wrong. It just wasn't looking at those things.

Why scanners fall short

Automated tools are excellent at checking things that can be decided by looking at code: is there an alt attribute, does this text meet a contrast ratio, does this input have a label. They're much weaker at anything that requires judgment or interaction.

A scanner can confirm an image has alt text. It can't tell you the alt text says "image123.jpg" or describes a chart without conveying the data. It can confirm a button exists. It can't press Tab twenty times to find out focus disappears behind a sticky header.

Automated testing tells you whether the code follows certain rules. Manual testing tells you whether a person can complete the task.

The Web Content Accessibility Guidelines (WCAG) 2.2 are written around outcomes for people, not rules for code. That's why a large share of the success criteria simply can't be fully verified by a machine.

Seven things scanners routinely miss

1. Keyboard traps and illogical focus order

Many people navigate entirely with a keyboard or with devices that emulate one. Custom dropdowns, carousels, date pickers, and modal dialogs are common trouble spots. A scanner won't notice that focus gets stuck inside an embedded widget (2.1.2 No Keyboard Trap) or jumps from the header to the footer and back (2.4.3 Focus Order).

2. Focus that's invisible or hidden

Removing the browser's focus outline with outline: none is still extremely common. Even when a focus style exists, WCAG 2.2 added 2.4.11 Focus Not Obscured (Minimum): the focused element can't be entirely hidden by things like sticky headers, cookie banners, or chat widgets. Scanners almost never catch this because it depends on scroll position and layout.

A simple, robust baseline looks like this:

:focus-visible {
  outline: 3px solid #4f43c9;
  outline-offset: 3px;
}

/* Keep focused elements clear of a sticky header */
html {
  scroll-padding-top: 5rem;
}

3. Meaningless accessible names

A scanner checks that a link or button has a name. It can't tell you that a page has twelve links all announced as "Read more," or an icon button announced as "button." Screen reader users often navigate by pulling up a list of links or buttons, so names need to make sense out of context.

<!-- Ambiguous -->
<a href="/pricing">Read more</a>

<!-- Clear, without changing the visual design -->
<a href="/pricing">
  Read more<span class="visually-hidden"> about pricing</span>
</a>

4. Form errors nobody hears

The classic failure: a user submits a form, a red border appears around a field, and nothing else happens. Sighted mouse users might spot it. Screen reader users get silence. Good error handling identifies the field, describes the problem in text (3.3.1 Error Identification), suggests a fix where possible (3.3.3 Error Suggestion), and moves focus or announces the error so it's actually noticed.

WCAG 2.2 also added 3.3.7 Redundant Entry: don't make people re-type information they already gave you in the same process, such as a shipping address on the billing step.

5. Small or crowded touch targets

New in WCAG 2.2, 2.5.8 Target Size (Minimum) asks that pointer targets be at least 24 by 24 CSS pixels, or spaced so that a 24-pixel circle around each target doesn't overlap another. Tiny close icons, inline pagination, and tightly packed social links often fail. Some tools can flag this now, but judging the exceptions (inline links in a sentence, for example) still takes a human.

6. Interactions that require precise movement

2.5.7 Dragging Movements requires an alternative to drag-only interactions, like sortable lists, sliders, or map pins. If the only way to reorder items is to drag them, people with tremors or those using voice control or switch devices may be locked out. The fix is usually simple: add "move up" and "move down" buttons, or let users type a value.

7. Content that breaks when zoomed

1.4.10 Reflow requires content to work at a width equivalent to 320 CSS pixels without two-dimensional scrolling, which is roughly what a 1280-pixel-wide window looks like at 400% zoom. Fixed-width containers, sticky elements that eat half the screen, and data tables are the usual offenders. Scanners don't zoom.

A 30-minute manual check

You don't need specialist tooling to catch most of the issues above. Pick your most important user journey, such as signing up, checking out, or requesting a quote, and do the following:

  1. Unplug the mouse. Complete the journey using only Tab, Shift+Tab, Enter, Space, Escape, and the arrow keys. Can you always see where focus is? Can you reach and operate everything? Can you escape every menu and dialog?
  2. Zoom to 400%. At a 1280-pixel-wide window, zoom the browser to 400%. Does anything get cut off, overlap, or require horizontal scrolling to read?
  3. Submit forms wrong on purpose. Leave required fields empty and enter invalid data. Are errors described in text, tied to their fields, and easy to find?
  4. Turn on a screen reader for five minutes. VoiceOver is built into macOS and iOS; NVDA is free on Windows. Navigate by headings and by links. Does the structure make sense? Do buttons and links say what they do?
  5. Check your own content. Read the alt text on key images and the headings on key pages. Would they make sense to someone who can't see the layout?

Write down every place you got stuck or confused. That list will be more valuable than any score.

Building accessibility into how you ship

Audits are most useful as a starting point, not a one-off event. The teams that sustain good accessibility tend to do a few things consistently:

  • Run automated checks in CI so regressions in the easy-to-detect issues never reach production.
  • Add a short keyboard-and-zoom check to the definition of done for new UI.
  • Build accessible patterns once in a shared component library, then reuse them everywhere.
  • Re-test key journeys after major redesigns or new feature launches.

Automated scanning and manual review aren't competitors. Use the scanner to catch the easy issues quickly and cheaply, and use people to find the barriers that actually stop your users.
